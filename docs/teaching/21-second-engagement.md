## ELI10

Think of a food truck. The truck (core) has the kitchen: stove, fridge, till. Each event (customer) brings a different
menu card, different ingredients and a different sign on the side (the engagement folder). Changing the menu should
never mean rebuilding the stove.

Before this sprint, the stove had one dish welded to it: the logistics prompt, table list, data generator and test
script lived inside `core/`. Phase 3a unbolted them and put them on the menu card (engagement.yaml and files in the
engagement folder). Then a completely different event, HVAC dispatch instead of shipping, was served from the same
truck without touching the kitchen.

Where the analogy stops: a food truck can cook anything that fits its stove. The kit can only serve customers whose
problem fits its shape: documents + a SQL database + an HTTP API + human approval for writes. A customer with a SOAP
system or a message queue would need a new connector in core (a generic one, useful to everyone).

## How a new customer is onboarded (the playbook, with real timings)

| Step | What was produced | Clock (executor, 2026-11-11) |
|---|---|---|
| 1. Discovery | `discovery.md`: problem, as-is/to-be, metrics, systems, actions and approvals | 09:04 |
| 2. Documents | 11 policy documents, one with a planted injection line for the red team | 09:06 (2 min for steps 1-2) |
| - | (Phase 3a: making core generic, a one-time cost, 09:07-09:19) | - |
| 3. Data | `extensions/seed.py` (stdlib, fixed seed, messy on purpose), `sql/001_field_tables.sql` (schema `field` + `sla_misses` view), table specs in YAML | 09:20-09:22 |
| 4. Systems | `services/mock-cmms/` (getWorkOrder, listWorkOrders, createDispatch) + exported OpenAPI contract; tools generated by the unchanged tool generator | 09:23 |
| 5. Agent | `prompts/agent-v1.txt` (`hvac-agent-v1`), `extensions/fake_agent.py`, refusal text, tool description, console examples | 09:23 |
| 6. Load | migrate + seed + ingest: 30 customers, 8 technicians, 48 equipment, 120 work orders, 11 documents in 35 chunks | 09:24 |
| 7. Golden set | 27 cases with the same category minimums; every fact computed by a query over the loaded data | 09:25 (first fake eval) |
| 8. Prove it | tests (golden minimums, sources exist, CMMS drift, CMMS rules, ETL mess, pause-approve-dispatch), live API run | 09:28 |

About **10 minutes of executor time** for the engagement itself (2 + 8), 24 minutes of wall clock including the 3a work.
A human FDE would take far longer: the interview, getting real exports and API access, and agreeing the golden set with
the customer are days of work in a real engagement. What the kit removes is the engineering part of that time.

## Teach-back check

<details><summary>1. Which logistics-specific things had to leave core/ before engagement #2 could be built?</summary>

Eleven gaps (DC-019..DC-029): table specs and the tier cleaner, foreign keys (one per table, no optional links), the seed generator, the ops tables migration (now engagement schema_sql), read-only grants on ops only, the scripted fake, the system prompt, the scoring's createTicket, the refusal text, the doc tool description, the console's example questions. Each became a config field or an engagement-owned file.
</details>

<details><summary>2. Moving the prompt out of core changes nothing for the model. How is that proven?</summary>

The runner records a SHA-256 of the exact prompt text in every report. The logistics prompt's fingerprint is 537c08f4c028 before and after the move, and a test asserts it. So the label agent-v1 still means the same text, and the real-eval results made before the move stay valid for --resume.
</details>

<details><summary>3. Why is the mock CMMS outside core/, and why does it enforce business rules?</summary>

It plays the customer's system, which the kit only reaches through its API. Its rules (on-call only after hours, skill must match the equipment, fee at most $150, one dispatch per order) are what a real system would reject, so the agent's mistakes show up as errors it must handle, like in production.
</details>

<details><summary>4. Engagement #2's golden facts (8 Premium customers, 3 open emergencies, 3 hours late) were computed by queries. Why not just write them down?</summary>

The data is generated. A number typed by hand can be wrong, and then the eval punishes a correct agent. Computing the facts from the loaded data (and pinning anchor records in the seed) keeps the data, the mock system and the golden set consistent. It is also the core of deferred idea B (Scenario Builder).
</details>
